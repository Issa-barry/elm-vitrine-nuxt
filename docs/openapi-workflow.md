# Types TypeScript depuis OpenAPI — workflow

Chantier du 27/08/2026. `elm-monolithe` publie un contrat OpenAPI 3.1
(`docs/openapi/client.json`) documentant l'API consommée par l'espace client
Nuxt. Ce dépôt génère ses types TypeScript à partir de ce contrat plutôt que
de les maintenir à la main.

## Chaîne

```
Laravel (elm-monolithe)
  → OpenAPI (docs/openapi/client.json, source autoritaire)
  → snapshot committée (openapi/elm-client.json, CE dépôt)
  → TypeScript généré (types/generated/elm-api.ts, `npm run api:types`)
  → alias lisibles (types/api.ts)
  → BFF Nuxt (server/api/client/*, server/utils/monolithClient.ts)
  → composants Vue
```

Le Bearer Sanctum reste exclusivement manipulé côté Nitro (`server/utils/
authSession.ts`) — cette chaîne ne change rien à l'architecture BFF, voir
`docs/environment.md`.

## Deux dépôts séparés — stratégie retenue

`elm-monolithe` et `elm-vitrine-nuxt` sont deux dépôts Git distincts. Options
considérées :

| Option | Verdict |
|---|---|
| A. Copier/committer une snapshot de `client.json` dans Nuxt | **Retenue** |
| B. Télécharger la spec depuis un artefact/release backend | Écartée pour l'instant — aucune release/artefact backend n'existe encore |
| C. Git submodule | Écartée — complexité d'usage disproportionnée pour un seul fichier JSON |
| D. Package de contrat publié | Écartée pour l'instant — pas de registre npm privé en place |

**A** est la plus simple et la plus robuste tant qu'aucune infrastructure de
publication (release, registre npm privé) n'existe entre les deux dépôts :
`elm-vitrine-nuxt` reste **buildable indépendamment**, sans checkout du
dépôt backend (important pour la CI, qui ne checkout qu'un seul dépôt à la
fois).

- **Source autoritaire** : `elm-monolithe/docs/openapi/client.json`.
- **Snapshot consommée par ce dépôt** : `openapi/elm-client.json` (committée,
  jamais éditée à la main).
- **TypeScript généré** : `types/generated/elm-api.ts` (committé, jamais
  édité à la main — bandeau `// This file was auto-generated by
  openapi-typescript` en tête).
- **Alias lisibles** : `types/api.ts` (écrit à la main, seul fichier à
  toucher pour exposer un nouveau type ou documenter une imperfection du
  contrat généré).

## Procédure après un changement backend

1. Le backend modifie un endpoint/contrôleur/Resource.
2. `elm-monolithe` régénère `docs/openapi/client.json` (déjà en place côté
   backend, déterministe).
3. Le commit backend est fusionné.
4. Côté Nuxt, sur un poste ayant les deux dépôts en frères
   (`../elm-monolithe`) : `npm run api:sync-spec` copie la nouvelle spec dans
   `openapi/elm-client.json`.
   - Sans ce checkout local (CI, autre poste) : récupérer `client.json`
     autrement (ex. copier depuis un PR backend) et le placer manuellement à
     `openapi/elm-client.json`.
5. `npm run api:types` régénère `types/generated/elm-api.ts`.
6. `npm run typecheck` signale immédiatement les adaptations nécessaires côté
   Nuxt (champ renommé, type resserré/élargi...).
7. Committer `openapi/elm-client.json` + `types/generated/elm-api.ts`
   ensemble avec les adaptations frontend, dans le même commit/la même PR.

## Vérification de déterminisme

```sh
npm run api:types
git diff --exit-code -- types/generated/elm-api.ts
npm run api:types
git diff --exit-code -- types/generated/elm-api.ts
```

Le deuxième `git diff --exit-code` doit sortir avec le code 0 (aucune
différence) — confirmé pendant ce chantier.

## Détection "spec modifiée mais types non régénérés"

Contrainte documentée plutôt qu'automatisée pour l'instant (les deux dépôts
n'ont pas de pipeline CI partagé) :

```sh
npm run api:types
git diff --exit-code -- types/generated/elm-api.ts
```

Si cette commande produit une différence dans un environnement où
`openapi/elm-client.json` est à jour, c'est que `types/generated/elm-api.ts`
n'a pas été régénéré après un changement de la snapshot — à intégrer comme
étape de CI Nuxt dès qu'un besoin se fait sentir (aucune dépendance CI
fragile entre les deux dépôts n'est nécessaire : la snapshot déjà committée
dans CE dépôt suffit, la CI Nuxt n'a jamais besoin de checkout
`elm-monolithe`).

## Imperfections connues du contrat généré

Voir les commentaires en tête de chaque fichier `config/client*.ts` pour le
détail par endpoint. Résumé (état au 27/08/2026) :

| Endpoint | Défaut constaté | Traitement |
|---|---|---|
| `GET/PATCH /v1/mobile/profile` | Réponse générée en `unknown[]` (un tableau) au lieu de l'objet réel `{user, profile}` | Réponse gardée entièrement à la main (`config/clientProfile.ts`) ; seul le corps PATCH (`UpdateProfileRequest`) est fiable et utilisé |
| `PATCH .../notification-preferences` | Corps de requête généré en `preferences: boolean[]` au lieu de `{preferences: {activite: boolean}}` | Payload et réponse gardés à la main |
| `GET /v1/mobile/activite` | `data` généré en `string[]` (les items réels sont des objets hétérogènes vente/logistique, jamais une Resource typée côté backend) | Items et filtres gardés à la main ; seuls les paramètres de requête (type/vehicule_id/dates/per_page) viennent du contrat |
| `GET /v1/mobile/depenses/mine` | `filters` généré en `unknown` (répétition, tous les endpoints paginés) ; `DepenseResource.statut` généré en `string` non fermé (le paramètre de requête équivalent, lui, a une énumération fermée) | `data` (items) dérivé du contrat, `statut` resserré manuellement, `filters` gardé à la main |
| `GET /v1/mobile/notifications` | `data[].type`/`titre`/`message` générés en schema vide (`{}`) — attendu (payload à structure libre), mais inutilisable tel quel | Gardé entièrement à la main |
| `GET /v1/mobile/vehicules/mine` | `en_livraison` généré en `string` au lieu de `boolean` | Type resserré manuellement |
| `GET /auth/me` | `context.client_id`/`proprietaire_id`/`livreur_id` générés en `null` seul (pas `string \| null`) — vraisemblablement inféré depuis un exemple de réponse où ces champs valaient `null` pour ce compte précis, pas depuis le vrai type nullable ; `email` généré en `string` non nullable alors qu'un compte inscrit par téléphone peut réellement n'avoir aucun email | `AuthContext` et le champ `email` d'`AuthUser` gardés/resserrés à la main (voir `config/auth.ts`) |
| `GET /v1/mobile/vehicules/{id}/commissions` | `VehiculeCommissionRow` propre ; réponse globale en union `VehiculeCommissionRow[] \| []` (cas "aucun véhicule accessible") qui cassait un spread TypeScript si dérivée par indexation | Type de l'item référencé directement via `components["schemas"]["VehiculeCommissionRow"]` plutôt que via la réponse |

Schemas confirmés **propres**, utilisés tels quels : `VehiculeEarningsRow`
(dashboard `par_vehicule`), `GET /v1/mobile/dashboard` (summary, hors
`filters.period` un peu lâche mais sans impact), `GET /v1/mobile/vehicules/
mine` (hors `en_livraison`), `GET /v1/mobile/vehicules/{id}/commissions`,
`POST /auth/login`, `GET /auth/me` (hors `context`/`email`), `UpdateProfileRequest`
(corps PATCH profil).
